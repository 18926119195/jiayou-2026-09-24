## 核心原理

### 1. 消息列表（Messages Array）

当你调用 DeepSeek API 时，请求体中有一个 `messages` 数组，例如：

```json
{
  "model": "deepseek-chat",
  "messages": [
    {"role": "system", "content": "你是助手"},
    {"role": "user", "content": "你好"},
    {"role": "assistant", "content": "你好！有什么可以帮助你的？"},
    {"role": "user", "content": "我叫张三"}
  ]
}
```

**关键点：你需要在每次 API 调用时，把之前所有的对话历史都一起传进去。**

### 2. 上下文保持的流程

```
用户第1次提问 → API返回回答（你存储：user问 + assistant答）
用户第2次提问 → 你发送：[系统消息 + 第1次问 + 第1次答 + 第2次问]
                API返回回答（你存储：user问 + assistant答）
用户第3次提问 → 你发送：[系统消息 + 第1次问 + 第1次答 + 第2次问 + 第2次答 + 第3次问]
                API返回回答
...以此类推
```

### 3. 区分不同聊天窗口的方法

这是**客户端（你自己）**负责的，不是 API 负责的：

| 方案 | 说明 |
|------|------|
| **多组消息列表** | 维护多个 `messages` 数组，每个对应一个聊天窗口 |
| **会话数据库** | 用数据库存储每个会话的历史，用一个 ID 关联 |
| **内存/文件存储** | 简单应用可以用内存或 JSON 文件存储 |

### 4. DeepSeek 官网的实现方式

官网聊天窗口的背后逻辑：

1. **前端**：每次发送消息时，把当前窗口的所有历史消息发送到后端
2. **后端**：可能是将历史缓存在服务器端，用一个会话 ID 标识（但最终传给模型的仍是完整历史）
3. **API 层**：将完整历史传给模型

## 简单示例代码

```python
import openai  # DeepSeek 兼容 OpenAI API 格式

client = openai.OpenAI(api_key="your-key", base_url="https://api.deepseek.com")

# 存储每个会话的消息
sessions = {}

def chat(session_id, user_input):
    if session_id not in sessions:
        sessions[session_id] = [
            {"role": "system", "content": "你是助手"}
        ]
    
    # 添加用户新消息
    sessions[session_id].append({"role": "user", "content": user_input})
    
    # 发送完整历史
    response = client.chat.completions.create(
        model="deepseek-chat",
        messages=sessions[session_id]
    )
    
    assistant_msg = response.choices[0].message.content
    sessions[session_id].append({"role": "assistant", "content": assistant_msg})
    
    return assistant_msg

# 同一个 session_id 会保持上下文
print(chat("window1", "我叫张三"))  # 模型会记住
print(chat("window1", "我叫什么？"))  # 会回答"张三"

# 不同的 session_id 是独立对话
print(chat("window2", "我叫李四"))  # 独立上下文
print(chat("window2", "我叫什么？"))  # 回答"李四"
```

## 缓存命中原理

由于每次请求都传递完整的对话历史，所以**历史的前缀部分**可以被缓存复用：

```
第1次请求：[sys, user1]                    → 缓存 [sys, user1]
第2次请求：[sys, user1, asst1, user2]      → 命中 [sys, user1]，只需计算新增部分
第3次请求：[sys, user1, asst1, user2, asst2, user3]
                                          → 命中 [sys, user1, asst1, user2]，只需计算 user3
```

**前缀完全匹配**的部分会被命中，只有新增的最后一两条消息需要重新计算。

## 缓存命中对价格的影响

DeepSeek 对命中缓存的 token 价格大幅降低（**约 10 倍差距**）：

| Token 类型 | 价格（参考）|
|-----------|-------------|
| 命中缓存 | 约 ¥0.1/M tokens（缓存读取）|
| 未命中 | 约 ¥1/M tokens（正常计费）|

举例来说：

```
对话长度 8000 tokens（前面都是历史）
新问题 200 tokens
总输入：8200 tokens

未命中：8200 × 1元 = 8200
命中后：8000 × 0.1元 + 200 × 1元 = 800 + 200 = 1000 元
```

**同一个会话越长、轮次越多，缓存命中率就越高，省的钱就越多。**

## KV Cache 是什么

在 Transformer 模型推理时，每生成一个 token 都要计算 attention，而 attention 需要计算 **Key（K）** 和 **Value（V）** 矩阵。

```
处理 "你好" → 计算 K1, V1 → 生成第一个 token
处理 "你好，请问" → 计算 K2, V2 → 生成第二个 token
...
```

**KV Cache = 把之前已经算好的 K、V 矩阵保存在显存中**，下次直接从这里接上，不用从头算。

## 缓存命中 vs 未命中的实际计算量

### 场景：8000 tokens 历史 + 200 tokens 新问题

**✅ 命中时**

```
8000 tokens 的 K、V 矩阵已经在显存中 → 直接复用
只需要计算 200 tokens 的 K、V → 接着推理
计算量 ≈ 200 tokens 的工作
```

**❌ 未命中时**

```
8000 tokens 全部要重新算 K、V
+ 200 tokens 新问题的 K、V
计算量 ≈ 8200 tokens 的工作（41倍工作量！）
```

## 为什么"回到历史窗口"会触发全部重算？

有几种典型情况：

### 1. 缓存过期（最常见）

```
窗口 A 在 10:00 聊完 → KV Cache 写入显存
10:30 关闭窗口
11:00 切回来（超过缓存存活期）→ KV Cache 已被清理
发送新消息时 → 服务端找不到对应前缀 → 全部 8000 tokens 重算
```

### 2. 被其他会话挤掉（显存不够）

```
显存只有 48GB

10:00 窗口 A 在算（占 20GB 显存）
10:30 窗口 B 开启算（占 25GB 显存）
11:00 窗口 C 开启算（占 30GB 显存）
       ↑ LRU 淘汰：窗口 A 的 KV Cache 被踢出显存

11:30 切回窗口 A → KV Cache 已不在 → 全部重算
```

### 3. 系统重启/模型切换

```
DeepSeek 服务端升级、部署、扩缩容
  → GPU 重启 → 所有 KV Cache 清空
  → 切换回历史窗口 → 全部重算
```

### 4. 前缀改变了（哪怕一点点）

```
历史窗口的 messages 数组 = [sys + 9条消息]

如果你编辑了某条历史消息
  → 前缀变了 → 之前缓存的 KV 全部对不上
  → 必须从第一个不同的位置开始重算
```

## 实际影响有多大？

| 情况 | 单次成本 | 用户感知 |
|------|----------|----------|
| 命中缓存 | ~¥0.001（便宜）| 响应快 |
| 全部重算 | ~¥0.01（贵 10 倍）| 首 token 慢 1-3 秒 |

**用户感知到的"卡顿"**：重算时，第一个 token 的延迟会明显增加（可能要等 2-5 秒），后续 token 就正常了。

## 那 DeepSeek 官网怎么应对？

### 1. **会话隔离的缓存**

```
窗口 A 的 KV Cache：显存地址 0x1000-0x2000
窗口 B 的 KV Cache：显存地址 0x2000-0x3000
窗口 C 的 KV Cache：显存地址 0x3000-0x4000
```

每个聊天窗口是独立的缓存单元，切换不影响。

### 2. **LRU 策略**

```
显存不够时 → 优先淘汰"最近最久没用"的会话
活跃窗口 → 留在显存 → 命中
冷窗口 → 被踢出 → 下次要重算
```

### 3. **定期刷新热门会话**

```
如果你 5 分钟内多次访问同一个窗口 → DeepSeek 会"加热"缓存
    → 延长在显存中的存活时间
    → 提高后续命中率
```

- 模型微调训练
- 性能 benchmark 评估
- **不是用来做推理缓存管理的**

```
DeepSeek 技术栈分工：

DeepSeek-V3/R1    → 模型本身
DeepSeek-Harness  → 训练评测框架（不是推理引擎）
SGLang            → 推理引擎（处理缓存调度）
vLLM              → 另一个推理引擎（也有 prefix caching）
```

**真正管缓存的是 SGLang（DeepSeek 官网用）或 vLLM**。

### 方案 2：客户端层面做"会话隔离"

```python
class ChatSessionManager:
    def __init__(self):
        self.sessions = {}  # session_id -> messages 列表
    
    def create_session(self, session_id, system_prompt):
        """每个会话独立的 system prompt 起点"""
        self.sessions[session_id] = [
            {"role": "system", "content": system_prompt}
        ]
    
    def send(self, session_id, user_input):
        """调用 API，每次带完整历史"""
        messages = self.sessions[session_id]
        messages.append({"role": "user", "content": user_input})
        
        # DeepSeek API 调用
        response = call_deepseek(messages)
        
        messages.append({"role": "assistant", "content": response})
        return response
```

这是一个非常好的问题！**理论上听起来很美，但实际上行不通。** 主要有以下几个原因：

## 1. 核心矛盾：KV Cache 不能"语义合并"

```
前缀 A: ["什么是", "资本论", "？"]  →  KV Cache A（每个位置精确对应）
前缀 B: ["介绍", "资本论"]         →  KV Cache B（每个位置精确对应）
```

即使 A 和 B 语义相似，它们的 KV Cache 也是**按 token 位置严格对齐**的。

```
KV Cache 的本质：
位置 1: K1, V1（基于前面所有 token 计算）
位置 2: K2, V2（基于前面所有 token 计算）
位置 3: K3, V3（基于前面所有 token 计算）
...
```

KV Cache 是**数学上唯一确定的**——给定一段 token 序列，KV Cache 是固定的，无法与"语义相似但 token 不同"的另一段 KV Cache 合并。

## 2. 语义哈希是"概率性"的，不适合做精确缓存

| | Prefix Cache | 语义哈希 |
|---|---|---|
| 匹配方式 | 字节/Token 级精确匹配 | 向量相似度 |
| 匹配结果 | 确定：相同 / 不同 | 概率：相似度 0.85 |
| 漏召回 | 不会 | 经常 |
| 误召回 | 不会 | **经常**（致命问题） |

**致命问题：误召回**

```
问题 A: "请介绍马克思主义"
问题 B: "请批评马克思主义"

语义相似度: 0.92（都谈马克思主义）
但答案应该完全不同！

如果误召回 → 返回 A 的答案 → B 的用户得到错误信息
```

而 prefix cache **绝不会**误召回，因为 token 序列不同 → 完全不命中。

## 3. 语义哈希本身的成本不低

```
生成 embedding：
  - 小模型（bge-large）：~几百 MB 参数
  - 每段文本计算：~几十 ms
  - 每 token 成本：~几百 FLOPs

生成 KV Cache：
  - 大模型（DeepSeek 671B）：~几百 GB 参数
  - 每段文本计算：~几秒
  - 每 token 成本：~几百亿 FLOPs
```

**所以语义哈希的成本 << KV Cache 重新计算的成本。** 从这点看，语义哈希似乎划算。

但是：

```
步骤 1: 计算输入文本的 embedding（~几十 ms）
步骤 2: 在缓存表中查找相似 embedding（~几 ms）
步骤 3: 如果找到匹配 → 但 KV Cache 还是不能用啊！
```

**问题来了：即使语义哈希匹配上了，KV Cache 还是 token-level 精确的，没有"语义版本的 KV Cache" 可以直接用。**

## 4. 业界为什么不用语义哈希？

看看主流方案：

| 厂商 | 缓存方案 | 是否语义哈希 |
|------|---------|------------|
| DeepSeek | Prefix cache（Token 精确匹配） | ❌ |
| Anthropic | Prompt caching（Prefix 精确匹配） | ❌ |
| OpenAI | 没有 prefix cache（GPT-4 系列） | ❌ |
| Google Gemini | Implicit caching（Prefix 精确匹配） | ❌ |

**所有厂商都选择 prefix 精确匹配**，原因就是上面说的几个：成本、确定性、正确性。

## 5. 那"近似匹配"的需求怎么办？

业界有一些替代方案，绕开"语义哈希做 KV Cache key"这个思路：

### 方案 A：规范化 + Prefix Cache

```javascript
function normalize(text) {
  return text
    .replace(/\s+/g, '')           // 去掉所有空白
    .replace(/[？?！!,。.]/g, '')   // 去掉标点
    .toLowerCase()
    .trim();
}

// "什么是资本论?" → "什么是资本论"
// "什么是  资本论？" → "什么是资本论"  
// 两个会被识别为相同 prefix
```

**比语义哈希保守，但不会误召回。**

### 方案 B：模板化 Prompts（最实用）

```javascript
// 不是用哈希匹配，而是限制用户输入只能填槽位
const template = `问题: {{question}}
要求: 详细回答`;

prompt = template.replace('{{question}}', userInput);
```

如果 100 个用户都问"什么是资本论"：
- 没模板：100 个不同 prompt，缓存命中率 = 1 / 100
- 有模板：100 个相同 prompt，缓存命中率 = 100 / 100

### 方案 C：缓存"输出"而不是"前缀"

这是**另一回事**，与 KV Cache 无关：

```
问题 A: "什么是资本论？"  →  答案 X（缓存 X）
问题 B: "介绍一下资本论" → 语义匹配到 A → 返回答案 X

但这是缓存 API 响应，不是缓存 KV Cache
适用场景：FAQ 问答、固定模板
不适用：需要 LLM 生成的复杂推理
```

## 6. 总结：为什么不能直接语义哈希做 KV Cache key？

| 问题 | 详细解释 |
|------|---------|
| **KV Cache 不可合并** | 语义相似的两段文本，KV Cache 在数学上是不同的 |
| **误召回致命** | 语义哈希的"近似匹配"会导致错误答案 |
| **行业标准** | 所有 LLM 厂商都用 prefix 精确匹配 |
| **替代方案更优** | 模板化 prompts + 规范化，能在保证正确性下提升命中率 |

**一句话：语义哈希做 KV Cache key 是一个看起来很美但走不通的路——因为 KV Cache 本身要求精确性，而语义哈希本质上是模糊的。**

如果你确实需要"语义级别"的缓存，那是另一个话题了（缓存 API 响应而不是 KV Cache），可以用 embedding + 向量数据库实现，但这又是完全不同的方案。

用户问了一个非常好的问题：为什么不能直接用语义哈希（比如文本的语义向量）作为缓存的 key？

让我深入思考这个问题。这涉及到几个层面：

## 为什么不能用语义哈希做缓存 key？

### 1. 推理成本问题

要计算语义哈希（embedding），本身就**需要调用一个模型**来生成向量（典型的 embedding 模型需要几十到几百 tokens 的计算）。对于 LLM 调用来说：

- 缓存的本质是：**避免重新计算 token-by-token 的 attention**
- 每次 LLM 推理中，最重的计算是**生成整个 prefix 的 KV Cache**（即每个 token 在每层 transformer 中的 key 和 value 向量）
- 如果你要先调用 embedding 模型计算语义哈希，这本身就有成本

### 2. 召回 vs 精确性问题

语义哈希本身是**近似的、概率性的**：
- 两段语义相近的文本，可能哈希值不同（漏召回）
- 两段语义不同的文本，可能哈希值相同（误召回）

```
"什么是资本论？"
"介绍一下资本论"
"请讲讲资本论是什么"
"今天天气怎么样？"

用语义哈希：
- 前三个可能被识别为相似 → 但 prompt 不同应该得到不同结果
- 如果误命中，会导致错误的响应
```

而 prefix cache 是**精确的、确定性的**：
- 完全相同的 token 序列 → 必然命中
- 不同的 token 序列 → 必然不命中

### 3. KV Cache 本身的特殊性

KV Cache 不能"语义合并"：
```
前缀 A: [token1, token2, ..., tokenN] → KV Cache A
前缀 B: [token1, token2, ..., tokenN-1, tokenM] → KV Cache B

即使 A 和 B 语义相似，它们的 KV Cache 也是 token-by-token 的，无法"融合"。
```

KV Cache 是**严格按 token 位置对齐**的，每个位置的 KV 值都由前所有 token 的 attention 计算得出。
